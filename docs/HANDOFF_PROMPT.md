## 2. 현재 아키텍처

```
상품 정의 + 페르소나 (+ 판매 정황 — 벤치마크에만 있다)
   ↓
사실팩(facts.py) — DSR, 부담률, 스트레스DSR, 우대조건 동시충족률, 금리격차, 판매정황 유무
   ↓
RAG 검색(rag/) — 금소법 6대 원칙 + 조정례. 평가 시 자기 사례 제외(정답 누출 차단)
   ↓
판정 — 세 방식
   · single    : 단발 1회 (호출 1/건)
   · debate    : 옹호자→페르소나→회의론자→페르소나→심판 5턴 (5/건)
   · ensemble  : 위 둘 병행. 우려는 합집합, **라벨은 single에서** (6/건)
   ↓
후처리 — ① 계산값과 모순되는 우려 기각  ② 계산값이 요구하는 최소 심각도로 승격
   ↓
산출 — 구조화된 우려 {유형, 심각도, 앵커, 확인방법, sources}
   ↓
표시(viewmodel.py) — 교차확인 × 심각도로 4계층 정렬 → report.py / ui/
```

**우려는 자유 텍스트가 아니라 구조화 객체다.** 유형은 `concern_taxonomy.json`의 15종.

## 3. 측정된 사실 — 이걸 전제로 작업할 것

기준선 `outputs/rate_A.json` · `qwen3:8b` · 정답셋 22건(pass 12/warn 5/fail 5) · 시드 1회 · `seed_base=7000`

| 지표 | single | debate | ensemble |
|---|---|---|---|
| 라벨 적중률 | **77.3%** | 47.6% | **77.3%** |
| 위험탐지 정확도 | 81.8% | 47.6% | 81.8% |
| **pass 정확도** | **8/12** | **0/11** | **8/12** |
| 우려 recall | 80.0% | 80.0% | **96.7%** |
| 우려 정밀도 | 36.9% | 32.0% | 33.3% |
| 깨끗한 상품 1건당 오탐 | 1.67개 | 2.18개 | 2.58개 |
| LLM 호출/건 | 1 | 5 | 6 |

**관대화 오류(위반인데 pass)는 모든 조건에서 0건이다.** 편향은 전부 보수 방향이다.

### 계층별 정확도 (ensemble, `rate_A`)

```
T1 즉시 조치  5/8  = 62.5%   (치명 + 교차확인)
T2 우선 검토 16/30 = 53.3%   (치명 단독 · 중대 + 교차확인)
T3 참고       8/16 = 50.0%   (중대 단독)
T4 접어두기   0/2  =  0.0%   (주의 이하)
```

**서열이 세 arm 모두에서 단조롭게 성립한다(역전 없음).** 설계는 검증됐다.
재산출: `uv run python scripts/analyze_ablation.py outputs/rate_A.json` 의 8절.
그 출력과 `concerns.py`의 `TIER_BASIS`가 어긋나면 `TIER_BASIS`를 고칠 것.

### 단발과 디베이트는 서로 다른 우려를 놓친다

```
정답 우려 30개 분해:  둘 다 잡음 19 · single만 5 · debate만 5 · 둘 다 놓침 1
각자 80%에서 천장을 치고, 병행하면 96.7%까지 오른다.
```

이것이 `ensemble`이 존재하는 이유다. 단, **라벨은 single에서 취한다** — debate는
깨끗한 상품 12건을 전부 warn으로 판정한다(0/11).

### 실행은 결정적이다

같은 `seed_base=7000`으로 재실행하면 라벨·우려 유형이 **전건 일치**한다
(`sev_A` vs `sev_B`로 확인). 관측된 차이는 표집 노이즈가 아니라 실제 변경 효과다.

## 4. 측정으로 부정된 주장 — 다시 쓰지 말 것

| 주장 | 왜 안 되는가 |
|---|---|
| "디베이트가 판정 정확도를 높인다" | single 77.3% vs debate 47.6%. **8B·14B 두 규모에서 재현** |
| "LLM 순응 편향을 억제한다" | 관대화 오류가 애초에 **0건**. 억제할 편향이 없다 |
| "신뢰도 스코어가 오답을 걸러낸다" | 저신뢰 오답률 40% vs 전체 42%. **재현성만 재고 정확성과 무관** |
| "근거 인용 규칙이 품질을 올린다" | naive와 라벨 지표 완전 동일 |
| "조정례 라벨 노출이 오탐 원인이다" | 5절 참고. **세 번의 개입이 전부 실패** |
| "앵커 실재 검증이 오탐을 줄인다" | 강등은 목록에서 빼지 않으므로 정밀도 불변. 6-5 참고 |

**쓸 수 있는 주장**
- RAG 그라운딩이 판정 정확도를 높인다 (조정례 제거 시 77.3% → 59.1%)
- 병행이 우려 recall에서 16.7%p 앞선다 (96.7% vs 80.0%)
- 계층 서열이 단조롭게 성립한다 (62.5% > 53.3% > 50.0% > 0%)
- 사실팩이 수치 환각을 정확히 차단한다
- **결함 16건을 측정으로 찾아 고쳤다** ← 가장 강한 카드

## 5. RAG 조정례는 건드리면 손해다 — 세 번 확인됨

오탐 원인을 RAG에서 찾으려 세 번 개입했고 **전부 실패**했다.

| 개입 | 결과 |
|---|---|
| 조정례를 통째로 제거 (`single_lawonly`) | 적중률 77.3% → **59.1%**, pass 8/12 → 5/12, 과잉위반 1.58 → 1.92 |
| 제목의 결론·판정 라벨만 제거 (`neutral_A`) | 오탐 2.58 → 2.50(노이즈), pass 8/12 → **7/12**, 위험탐지 81.0 → 76.2% |
| 앵커 실재 검증 (강등) | 정밀도·오탐 **불변**. 올바르게 3값 판정하면 대상이 16개 → 1개 |

**전제는 참이었다.** 설명의무 오탐 12건 중 8건에서 CASE-009("장기 적금 중도해지 불이익
설명 부족")가 함께 검색됐고, 그 8건이 전부 "중도해지 설명 부족"이라 답했다(검색 안 된
4건은 각기 다른 얘기를 했다). **그런데 조치는 다 실패했다** — 판단요지 본문에 결론이
남아 있고, 조정례를 빼면 정상 판매 예시(CASE-006/008) 2건을 같이 잃기 때문이다.

검색 결과의 72%가 조정례이고 그중 74%가 fail/warn이다. RAG의 기여가 **판정 라벨 노출에
상당 부분 의존**한다는 뜻이라 좋은 소식은 아니지만, 건드리면 더 나빠진다.

기록: `dispute_cases.json`의 `_meta._neutral_title_rolled_back`

## 6. 오탐 대책 — 지금까지 통한 것과 안 통한 것

기준선 오탐: **깨끗한 상품 1건당 2.58개**(ensemble). 정밀도 33.3%.

### 통한 것 — 계산으로 반증 가능한 유형에 규칙 걸기

```
규칙 있는 유형의 오탐  20개 (31%)
규칙 없는 유형의 오탐  45개 (69%)
```

예금자보호 한도·원금손실·DSR·고령자·만기일시상환은 깨끗한 12건에서 **오탐 0건**이다.

**금리오인 규칙** (`rate_display_misleading`): 우대조건이 없거나 금리 격차가 없으면
"최고금리 위주 표시 오인"은 성립하지 않는다. **오탐 −7 / 정답 손실 0.**
사전 시뮬레이션 예측과 실측이 정확히 일치했다.

**설명의무 규칙 A** (`explanation_insufficient` + `has_sales_context`): 설명의무는
판매 행위에 대한 판정이므로(verify_with도 "설명 확인서·녹취 이행률") 아직 팔지 않은
설계 단계에서는 범주 오류다. 정황이 없으면 기각한다.
**벤치마크 점수는 안 오른다**(22건 전부 정황 있음). 실제 리포트 경로에서만 걷힌다.

### 방법론 — 규칙은 돌리기 전에 손익을 계산할 수 있다

기존 결과 JSON에 규칙을 적용해보면 **LLM 재실행 없이** "오탐 −N / 정답 −M"이 나온다.
금리오인 규칙은 이 방식으로 예측(−7/0)하고 실측(−7/0)이 일치했다.
**손익이 안 맞는 규칙은 구현하지 않는다.**

### 결정 대기 중 — 사례ID 앵커 제거

앵커가 다른 사례(`CASE-xxx`)만 가리키는 우려. 자기 상품·페르소나가 아니라
검색된 이웃 사례를 근거로 재활용한 것이다.

```
ensemble 9개  →  오탐 8 / 정답 1  (정밀도 11%)
debate  16개 · single 2개  ← 회의론자가 이웃 사례를 베낀다

제거 시:  정밀도 33.3% → 35.9%,  깨끗한건 2.58 → 2.00개,  정답 −1
강등 시:  **효과 0** (목록에서 안 빠지므로 정밀도 불변)
```

**효과를 내려면 제거해야 하는데, 작업원칙 4번("지우지 않고 정렬한다")과 충돌한다.**
미결이다.

### 남은 최대 오탐원

`explanation_insufficient` 15개 — 깨끗한 12건 **전부**에서 나온다. 계산으로 반증이
안 되고, 정황 기반 규칙은 벤치마크에서만 작동한다(실제 경로엔 정황이 없다).

## 7. 다른 작업 사본의 실험 (미검증) — 검증 레이어

**이 저장소에 코드도 결과 파일도 없다.** 다른 사본에서 Colab `qwen3:14b`로 수행됐다.

| 실험 | 주장 |
|---|---|
| 1. 8B vs 14B | 디베이트의 저조한 판정은 **모델 한계가 아니라 구조적 결함**. 같은 모델이 혼자면 pass 11/12, 회의론자가 앞에 붙으면 2/12 |
| 2. 검증 레이어 v1 | 회의론자 주장을 심판 전에 코드로 검증 → 45.5% → 81.8% |
| 3. v2 사전 차단 | 발화 전에 성립 불가 유형 차단 → **95.5% (21/22)**, 단발 +13.6%p |

**실험 1의 통제는 깨끗하고 결론은 신뢰할 만하다.** 8B·14B 재현이라 흔들리지 않는다.
실험 2의 "고쳐진 9건이 전부 gold=pass"도 진단이 옳았다는 직접 증거다.

### 검증 전에는 95.5%를 주장하지 말 것 — 세 가지 공백

1. **우려 recall이 보고되지 않았다.** v2는 회의론자 발화 전에 유형을 차단하는데
   (깨끗한 상품에서 9개 유형), 이 시스템의 검증된 강점이 우려 발굴(96.7%)이다.
   무엇을 대가로 얻었는지 모르는 상태다. **결과 JSON만 있으면 재실행 없이 계산된다.**
2. **차단 근거 절반이 실제 경로에서 발동하지 않는다.** 사실팩 모순은 어디서나 작동하지만
   판매 정황 기반 차단은 **벤치마크에만 정황이 있어** 실제 상품 설계에서는 안 걸린다.
   +13.6%p 중 얼마가 벤치마크 전용인지 분해되지 않았다.
3. **키워드를 정답셋 22건을 보며 조정했다**(본인들이 밝힘). 부정문 처리 버그 수정은
   정당하지만, 그 외 임계값도 적합됐다면 3건 차이의 실효 크기가 불명확하다.
   특히 "CASE-010/011이 v2에서 맞았으므로 정답셋 결함이 아니다"는 **성립하지 않는다** —
   그 케이스를 보며 조정한 규칙이 그 케이스를 맞히는 건 독립 증거가 아니다.

### 코드를 받으면 할 일

**로컬 8B에서 검증 레이어를 재현한다.** GPU가 필요 없고 45~55분이다.

```
14B + 검증 레이어   95.5%   ← 이미 있음
8B  + 검증 레이어   ?       ← 이걸 재면 갈린다
8B  단독           77.3%   ← rate_A
```

8B에서도 크게 오르면 개선 원인이 **모델 크기가 아니라 검증 레이어**로 확정된다.
실험 1이 자기 결론을 굳힌 것과 **같은 기준을 자기 개선안에도 적용**하는 것이다.

지금도 1건 = 4.5%p다. pass 12건은 확보됐으나 warn·fail이 5건씩뿐이라
**위반 케이스 쪽 표본이 병목**이다. 유형별 정답도 편중돼 있다
(`explanation_insufficient` 7건 vs 9개 유형이 1건씩).

### 10-4. CASE-010/011 라벨 검토

세 조건 모두에서 틀렸다. CASE-011은 CASE-004와 위반 유형이 같은데 라벨이 다르다.
**모델 출력이 아니라 데이터를 보고 판단할 것.**

### 10-5. 벤치마크 상품에 `clauses` 채우기

정답셋 22건 중 약관 조항이 있는 상품이 **0건**이다. 실제 상품 정의에는 4개씩 있다.
모델이 "약관 제10조"라고 쓰는 게 근거가 아니라 형식 채우기이고, 지금은 검증할 원본이 없다.

### 10-6. 조정례 원문 교체 (fss.or.kr)

공개 현황을 확인했다.

```
분쟁조정결정례  814건 (은행ㆍ중소서민 184건)  첨부 .hwp (일부 .pdf)
분쟁조정사례    201건 (은행ㆍ중소서민  25건)  첨부 .hwp
가장 값나가는 것: "금융분쟁조정사례집 제2권" — PDF로도 제공되어 파싱 가능
```

**주의 세 가지.** ① 조정례는 분쟁 사건 모음이라 **pass 케이스가 구조적으로 없다**
— 정상 사례는 금융상품 한눈에 실 상품에서 따로 구성해야 한다. ② 은행 권역 184건도
상당수가 KIKO·DLF·라임 등 파생상품이라 적금·예금·카드와 도메인이 다르다.
③ 저작권 정책이 공공누리가 아니라 **개별 협의 방식**이다. 요지·출처만 담고
원문 복제를 피하는 현재 구조(`decision_gist` 한 줄)를 유지할 것.

## 12. 작업 원칙 (이 프로젝트에서 지켜온 것)

1. **측정 없이 개선을 주장하지 않는다.** 가설 10개 이상이 측정으로 뒤집혔다.
2. **조용히 잘못된 값을 만드는 코드를 경계한다.** 고친 결함 16건 중 7건이 그 유형이었다.
3. **데이터 부재를 부정 사실로 해석하지 않는다.** `None`(모름)과 `False`(아니오)를 구분한다.
   규칙은 `not f.x`가 아니라 `f.x is False`로 쓴다.
4. **지우지 않고 정렬한다.** 우려는 기각보다 계층화가 안전하다.
5. **가공 데이터에는 표시를 남긴다.** `[MOCK]`, `_meta.caveat`, `조정사례(가공)`.
6. **정답셋에 맞춘 최적화와 실제 개선을 구분한다.** 벤치마크 점수만 오르는 조치는
   그 사실을 명시하고, 실제 성능으로 주장하지 않는다.
7. **계산 계층에 UI를 넣지 않는다.** `viewmodel.py`에 streamlit이 들어오면 테스트가 죽고,
   UI를 갈아엎을 때 판단이 같이 사라진다(changhwan 머지에서 실제로 겪었다).
